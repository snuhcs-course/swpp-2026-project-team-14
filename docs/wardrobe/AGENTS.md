# StyleMate 작업 지침

이 문서는 이 저장소에서 수행하는 사용자와 AI의 개발 작업에 적용한다. 현재 개인 기능 개발을 위한 지침이며, 팀 전체가 승인한 공통 규칙으로 간주하지 않는다. 사용자의 명시적 요청과 팀의 확정된 프로젝트 규칙을 우선한다.

옷장 작업의 기준 문서는 `docs/wardrobe/`다. 공통 실행·체형 기능과 연결되는 작업은 [백엔드 실행 안내](../../backend/README.md)와 [체형 기능 설계](../body-analysis/02-design.md)를 함께 확인한다. 문서에 표시된 현재 구현과 향후 설계를 구분하고 실제 코드를 대조한다.

## 프로젝트와 담당 범위

- 프로젝트는 4명이 12주 동안 진행하며, 이터레이션은 2주 단위다.
- 기술 스택은 Android Kotlin·Jetpack Compose, Django, MySQL, AWS S3, 외부 AI API 또는 Python 모델, Azure VM이다.
- 현재 담당 기능은 사진 등록·AI 특징 추출·사용자 수정·가상 옷장 저장이다. 해당 기능의 Android FE와 Django BE를 함께 개발한다.
- 공통 FE·BE 초기 설정, 프로필·체형 기능, 인프라는 다른 담당자의 작업과 연결한다. 기존 구조와 담당 범위를 확인한 뒤 공통 파일을 변경한다.
- 예정된 기술과 디렉터리가 이미 구현되었다고 가정하지 않는다. 실제 상태는 코드와 [architecture.md](architecture.md)를 확인한다.

## 작업 전 확인

1. 현재 브랜치와 미커밋 변경을 확인하고, 기존 사용자 변경을 보존한다.
2. 요구사항, 기존 구조, 영향 범위를 확인한다.
3. [architecture.md](architecture.md)를 읽어 파일 위치와 구성요소의 역할을 확인한다.
4. 옷장 작업에서는 [design.md](design.md), [wardrobe-spec.md](wardrobe-spec.md), [wardrobe-types.md](wardrobe-types.md), [wardrobe-flow.md](wardrobe-flow.md)를 필요한 범위에서 확인한다. 실행·환경 설정은 [local-development.md](local-development.md)를 따른다.
5. 문서의 제안·예정 상태와 확정·구현 상태를 구분한다. 문서 간 충돌이 있으면 사용자 요청과 실제 구현을 확인하고 관련 문서를 일관되게 정리한다.

## 구현 원칙

- 기존 구조와 코드 스타일을 우선하고 변경 범위를 최소화한다.
- 현재 요구에 필요하지 않은 파일, 추상화, 의존성을 추가하지 않는다.
- wardrobe FE는 팀 Android 프로젝트 내부, wardrobe BE는 backend 내부에 배치한다. 별도 앱·서버 프로젝트를 중복 생성하지 않는다.
- 실행은 팀의 `frontend/` Android 프로젝트와 `backend/manage.py`·`config.wsgi`로 통일한다. 개인 테스트용 앱·Django 설정·DB 실행 래퍼는 다시 만들지 않는다. 서버 환경변수는 `backend/.env` 또는 배포 환경에서 설정한다.
- 구체적인 Android 패키지와 Django 앱 구조는 기본 세팅을 확인한 뒤 결정한다. architecture.md의 예정 구조를 구현된 경로로 취급하지 않는다.
- API 계약, 데이터 허용값, UI 표시명 변경 시 FE·BE·AI·추천 기능에 미치는 영향을 확인한다.
- Gemini는 이름·분류·색상표의 대표색 1~2개만 생성한다. 색상은 HEX 배열로 저장하며 사진에서 고른 색을 포함해 최대 5개다. 상세 소매 선택과 러블리 스타일은 사용하지 않고 실측 소매길이는 유지한다. 실측은 ARCore 계산 또는 사용자 입력으로 관리한다. 착용 정보와 격식·여밈·디테일·어깨 구조·넥라인 속성은 저장하지 않는다. 어깨너비 등 실측 항목은 유지한다.
- AI 비밀 키와 저장소 자격 증명은 서버에서 관리한다. 비밀값, 실제 사용자 사진, 접근 토큰을 코드·문서·Git에 포함하지 않는다.

## architecture.md 유지 규칙

**기능 구현 파일의 추가·이동·이름 변경·삭제 또는 역할 변경 시 같은 작업에서 docs/wardrobe/architecture.md를 갱신한다.**

- 기능을 설명하는 데 필요한 소스·테스트·연결 설정을 중심으로 작성한다. 저장소 전체 파일 목록을 만들지 않는다.
- 실제 경로를 디렉터리 트리로 표시하고 각 경로 옆에 `# 한국어 역할 설명`을 짧게 붙인다. 긴 패키지 경로는 한 줄로 합친다.
- 별도 파일별 역할 표를 만들거나 트리의 설명을 반복하지 않는다.
- .gitignore, 빌드 도구·래퍼, 패키지 선언용 파일, 인프라 설정, 임시 연결 테스트, 캐시·비밀 설정 등 기능 설명에 불필요한 항목은 생략한다.
- 추가·이동·삭제 시 해당 트리 경로와 주석을 함께 수정한다. 생략 대상 파일만 바뀌면 문서 수정은 필요하지 않다.
- 실제 구현과 미구현 범위를 짧게 구분한다. 상세 설계·실행 방법은 담당 문서에 두고 링크로 참조한다.
- 수정 후 트리에 표시한 경로·역할·문서 링크를 실제 구현과 대조한다.

## 문서 작성 원칙

### 앱 UI 문구

- 버튼·제목·항목명은 짧고 익숙한 말로 작성한다. 불필요한 괄호 설명을 붙이지 않는다. 예: `촬영하기`, `암홀`, `소매끝`.
- 화면에는 현재 행동에 필요한 안내만 간결하게 표시한다. 같은 의미의 설명·진행 안내를 여러 곳에 반복하지 않는다.
- 구현 방식·개발 상태·상세 측정 기준은 문서에 둔다. 사용자의 판단에 필요한 미저장 상태·추정값 표시·오류 복구 안내는 짧게 유지한다.
- UI 표시명을 줄여도 데이터 키·측정 방법·단위의 의미는 유지한다. 기울기 수치·치수별 AR 추정 문구는 표시하지 않으며 배경 제외 기능은 사용하지 않는다. AR 측정 출처와 계산은 유지한다.

### 개발 문서

- 옷장 문서는 `docs/wardrobe/`에서 관리한다. 체형 문서는 기존 `docs/body-analysis/`를 유지하며, 같은 목적의 문서 폴더를 중복 생성하지 않는다.
- 명세는 객관적인 한국어 서술체로 작성하고 1인칭·대화체·장식용 이모지를 사용하지 않는다. 실제 UI 문구는 예외다.
- 확인된 사실, 설계 제안, 미정 항목을 구분한다. 추정값을 원본 시안의 정확한 값으로 서술하지 않는다.
- 필드 정의는 wardrobe-spec.md, 종류 코드·표시명은 wardrobe-types.md, 화면 동작은 design.md, 파일 위치·역할은 architecture.md에 둔다. 다른 문서에서는 링크로 참조하여 중복을 줄인다.
- 모든 의류 코드에 한국어 의미를 제공한다. JSON 예시와 본문 규칙을 일치시킨다.

## Git과 배포

- 기본 흐름은 main → develop → 기능 브랜치이며 기능 PR의 대상은 develop이다.
- 현재 옷장 기능 브랜치는 feature/wardrobe다. 이 이름을 다른 작업에서도 무조건 사용하지 않는다.
- main·develop에 기능 변경을 직접 작성하지 않는다. 커밋·푸시·PR은 사용자가 요청하거나 해당 작업 범위에서 승인한 경우 수행한다.
- 커밋 전 관련 빌드·테스트·린트를 확인한다. 실행 환경이나 검사 설정이 없으면 미실행 항목과 이유를 보고하며 통과로 표현하지 않는다.
- 문서만 변경한 경우 문서 링크·예시·구조 일관성을 검증하고 앱 빌드·테스트는 해당 없음으로 보고할 수 있다.
- 커밋 메시지는 feat:, fix:, refactor:, docs:, test:, chore: 등의 접두사를 사용하되 팀의 확정 규칙이 있으면 따른다.
- 현재 main의 backend 변경은 이미지 빌드·푸시·배포 설정 변경으로 이어진다. VM이 중지되어 있다는 이유로 검증을 생략하지 않는다.
